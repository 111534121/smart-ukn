# 老師與行政端報告重點（T36）

準備人：張晴茹。整理日期：2026-10-22。可直接照以下順序報告；功能示範使用虛構帳號與資料，不代表學校正式上線。

## 開場說明

這次把老師端做成可以處理事情的流程：先從今日工作台看到需要處理的項目，再到出缺勤、請假、關懷或班級通知完成操作。行政端補上宿舍審核，學生與家長能看到同一筆審核結果；一般行政案件則提供處室分流、補件及結案。重點是資料來源、判斷邏輯與權限都能解釋，不只展示畫面。

## 老師端：問題、資料與邏輯

### 扣考預警及請假串接

問題：只顯示「快扣考」不夠，必須能說明次數／時數與適用門檻，並知道請假資料從哪裡來。

流程：`attendance/sources.py` 讀取缺曠課 → `attendance/policy.py` 依同學期、課程總時數、假別及適用條件計算 → 教師班級出缺勤顯示結果，並對照請假來源。缺少實際時數或課程總時數時標示估算；特殊假別待核定時提示人工核對。

一般缺曠門檻依目前保存的校規快照為全學期授課時數三分之一；提前提醒比例是產品設定，不是校規。系統顯示門檻預警，不代替校方正式扣考處分。校規來源及完整示範見 `扣考與宿舍整合示範.md`；後續校規版本仍須由團隊確認。

請假不是另造完整校務系統：目前以模擬來源表供教師端讀取／審核；核准請假不會直接抹除缺曠課紀錄，須對應課程與節次。未宣稱已接上學校正式資料庫。

### 今日工作台、關懷追蹤與通知

工作台彙整課表、待審事項、班級預警、到期關懷與通知回條。關懷紀錄含追蹤日期、處理階段及結果；結案後不再列入待追蹤，重新開啟後可繼續追蹤。

通知以收件者名單限制讀取；「已讀」與「已回條」分開計算。同一學生更新回條不重複計數；家長只能查看子女資料，不能代填；提醒只送未回覆的指定學生。老師以導師班與本人發出的通知限制查詢，不因前端隱藏入口而省略後端權限檢查。

## 行政端：問題、資料與邏輯

### 宿舍申請審核

有宿舍權限的行政帳號才能查看及推進審核；學生／家長只能讀取自己或綁定子女的結果。資格審查、床位排序、床位分配、繳費到完成入住依序推進；分配階段需床位，退回需原因，結案禁止再推進。MySQL 更新帶入原狀態比對，避免舊畫面覆蓋新狀態；歷程包含操作者與時間並寫稽核紀錄。

### 處室行政案件

學生送件 → 對應處室受理 → 要求補件 → 學生重新送審 → 承辦人結案。轉交後舊處室不能繼續讀取案件／附件；學生只能操作自己的案件，附件透過登入且有案件權限的端點取得。

此工作台目前使用 campus_store.json 及同層私有附件，不是 MySQL 案件資料表；與原本請假、宿舍等業務流程分開。五種處室示範及新流程以現行文件為準，尚未提交的新變更不當成已上線成果。

## 可交給王博慶彙整的資料表與來源對照

以下是本人使用範圍，不取代全組完整 ER 圖。最終型別、外鍵及欄位以 smart_ukn.sql／增量腳本與實際資料庫為準。

| 功能 | 來源與關鍵欄位 | 關聯／用途 |
| --- | --- | --- |
| 登入與權限 | users：user_id、username、role、student_id、advised_class、can_manage_dorm | 綁定學生、導師班與宿舍管理能力；行政人員不等於系統管理員 |
| 班級學生 | students：student_id、class_name、dept_id；departments：dept_id | student_id 為跨功能學生識別；班級欄位限制導師查詢 |
| 課表／授課時數 | class_schedule：student_id、class_name、course_name、teacher；course_map：course_name、semester_hours | 課程及老師對應；實際總時數不足時不得默認成正式判定 |
| 缺曠課 | attendance_records：id、student_id、date、course_name、type、hours、exam_policy | 依學生／課程／學期彙總，假別與例外條件影響計入時數 |
| 請假來源 | leave_requests：id、student_id、leave_type、start_date、end_date、periods、status | 供老師讀取及審核；與缺曠課以學生及期間／節次對照，不是單靠一個狀態直接刪紀錄 |
| 關懷紀錄 | counseling_records：id、student_id、class_name、counselor_username、follow_up_date、tracking_status、tracking_result | 對應學生、導師班及紀錄作者，限制私密內容的存取 |
| 班級與成員 | class_groups：class_name；class_group_members：class_name、student_id | 班級與學生的成員關係，協助決定通知收件名單 |
| 通知與回條 | class_notices：id、sender_username、reply_required；class_notice_recipients：notice_id、student_id、read_at、reply、reply_at | 一則通知多個收件者；讀取與回覆依收件人隔離 |
| 宿舍 | dorm_applications：id、student_id、semester、stage、status、bed、history_json | 學生／學期唯一申請；審核進度供學生與家長共同讀取 |
| 修改稽核 | audit_logs：table_name、record_id 及操作者／時間資訊 | 指向重要異動，不把晤談內容等敏感全文當作必要稽核資料；全組稽核範圍由T08另外彙整 |
| 行政案件與處室 | campus_store.json：admin_cases、admin_offices、admin_office_catalog、admin_workflows；admin_case_files | 本機JSON與私有附件，沒有宣稱已有 MySQL 關聯式案件表 |

示範資料來自 app.py、dashboard/demo_data.py 與 seed_report_demo.py 等示範腳本；請假／宿舍流程驗證另使用隔離資料庫，未取得學校正式來源表。本表已準備供王博慶引用，不代表已代全組完成T21或已傳送訊息。

## 一筆完整示範：老師發現預警到行政結果同步（約五分鐘）

1. 用 teacher1 登入，打開班級出缺勤，選學生 S112001 的「【示範】」課程；假設學期總時數54小時，說明17小時未達、18小時達門檻、19小時超過。這是虛構案例，真實課程不能直接套54小時。
2. 展開同一學生的【模擬串接】請假紀錄，說明來源表、期間／節次與審核狀態；不要把核准請假解釋成直接消除缺席。
3. 示範選定學生提醒／需回條的通知，再用學生帳號回覆，回到老師端確認已讀與已回覆數分開顯示。若要寫入，先使用示範環境並保留資料。
4. 換 dorm_demo 示範宿舍行政端；選標示為示範的申請，說明階段、床位、退回原因與歷程。已結案案例只讀取，不為展示而覆寫。
5. 換 student1／parent1 看同一筆申請，說明學生與家長看到相同結果，但家長不能審核。結尾指出驗收在本機，不等於正式上線。

示範帳號僅限虛構資料環境；密碼及詳細操作沿用既有本機示範文件。報告前先確認服務與示範紀錄仍存在。若既有案例不齊，於獨立示範環境執行 seed_report_demo.py，不匯入正式校務資料。
