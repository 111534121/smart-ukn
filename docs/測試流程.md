# 測試流程（T11）

改完程式、要 push 之前，**一定先跑一鍵檢查**。全部通過才 push、開 Pull Request。

## 1. 一鍵檢查

在 `smart-ukn` 專案資料夾（有 `app.py` 的那層）執行：

```
python check_all.py
```

| 指令 | 什麼時候用 | 大約多久 |
| --- | --- | --- |
| `python check_all.py` | push、開 Pull Request 之前 | 1 分鐘 |
| `python check_all.py --quick` | 平常改程式，想快速確認有沒有弄壞 | 15 秒 |
| `python -m pytest tests/test_xxx.py` | 只想跑某一個測試檔 | 幾秒 |

第一次使用要先安裝測試套件：`pip install -r requirements-dev.txt`

檢查會用**示範資料**，不會動到 MySQL，也不會寄出 Email，可以放心重複執行。

### 會檢查什麼

| 項目 | 檢查內容 | 沒過怎麼辦 |
| --- | --- | --- |
| 分支與存檔狀態 | 目前在哪個分支、有沒有還沒 commit 的檔案 | ⚠️ 只是提醒，記得 `git add`、`git commit` |
| Python 語法 | 所有 `.py` 都能執行 | 照提示的檔案和行號修正 |
| JavaScript 語法 | `static/` 的 `.js` 沒有打錯（有裝 Node.js 才檢查） | 照提示修正 |
| 合併前常見錯誤 | 殘留的 `<<<<<<<` 衝突標記、`.env` 被上傳、改了網頁卻沒更新 `static/sw.js` 的 `CACHE_VERSION` | 解決衝突／移除檔案／把版本號加 1 |
| pytest 自動測試 | `tests/` 底下全部測試，包含權限矩陣 | 看報告裡的失敗原因 |
| 全站功能檢測 | `self_check.py` 的 60 項功能流程（`--quick` 時略過） | 看報告裡的失敗原因 |

### 報告

每次執行會存一份報告到 `evidence/check_reports/檢查報告_分支名稱_日期時間.md`（只留在自己電腦，不會上傳）。開 Pull Request 時可以把報告內容貼在說明裡。

- ✅ 通過　❌ 沒通過　⚠️ 提醒　⏭️ 略過（例如沒裝 Node.js）
- pytest 的「已知問題/略過」（xfail）不算失敗：那是權限矩陣裡標 `*` 的格子，代表組內知道還沒修好的問題。

## 2. GitHub 自動檢查

`.github/workflows/check.yml` 會在每次 push、開 Pull Request 時，自動在 GitHub 上跑一次 `check_all.py`。

- Pull Request 頁面下方出現**綠色 ✓**：全部通過。
- 出現**紅色 ✗**：點「Details」看哪一項沒過，在自己電腦修好、commit、push，會自動重跑。
- 第一次使用：到 GitHub 專案的「Actions」分頁確認有開啟。

## 3. 每週四合併流程（晴茹）

1. 打開任務清單，篩選狀態「待合併」。
2. 每個 Pull Request 先看 GitHub 自動檢查是不是**綠色 ✓**，紅色的退回給負責人。
3. 按 Merge；合併完在自己電腦切到 `main`、`git pull`，再跑一次 `python check_all.py`，確認合在一起之後也沒問題。
4. 回任務清單把那幾列改成「已合併」。

## 4. 新增功能時要一起補的測試

每個功能至少要有：

- **一個正常操作**：例如老師新增一筆關懷紀錄成功。
- **一個異常或權限情況**：例如老師不能看別班、學生看不到。

新的 API 還要在 `tests/permission_matrix.csv` 加一列，寫清楚每種身分應該是 `OK`、`401` 還是 `403`。沒加的話，`test_permissions.py` 會失敗提醒。

測試檔放在 `tests/`，檔名用 `test_功能名稱.py`，可以參考：

| 想測什麼 | 範例檔 |
| --- | --- |
| 登入後的完整流程 | `tests/test_counseling.py` |
| 不同身分的權限 | `tests/test_class_overview.py` |
| 已刪除的功能不能再出現 | `tests/test_removed_features.py` |
